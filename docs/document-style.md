> 状态：契约 · 适用版本 1.33.0 · 最后核对 2026-11-15

## 为什么要有这一页

一份文档「清晰」不靠作者自觉，靠三件事可被机器检查：**结构一致**（每页同样骨架）、**可导航**（长页有目录、末尾有去处）、**判断可做**（页首告诉你这份算不算规范）。

读者打开一页时应该三秒内知道：这是什么、还算不算数、从哪开始看。三者缺一项，这页就是「能读但不清楚」。

## 页面骨架

每一页从上到下固定这几段，缺哪段补哪段：

```text
# 标题                     ← 唯一 H1，名词短语
> 状态：… · 适用版本 … · 最后核对 …   ← 状态行
（可选，≤5 行）这份文档回答什么问题
## 目录                   ← 长页才要，见下文
## 正文各节
## 相关文档                ← 3–6 条，给下一步去处
```

## 状态行

H1 下面紧跟一行 blockquote，写死三件事：

```markdown
> 状态：契约 · 适用版本 1.33.0 · 最后核对 2026-11-15
```

状态只能取下面七种之一。它决定读者要不要按它办事：

| 状态 | 含义 | 和代码冲突时 |
| --- | --- | --- |
| `契约` | 改代码前必读的硬约束（架构、约定、验证、数据模型、文档写法） | 以代码为准，并回来改文档 |
| `规范` | 跨功能规则（文案、chips、许可证、流派、健康度 unknown） | 同上 |
| `设计（已实施）` | 这一版就是这么做的，含取舍理由 | 同上 |
| `方案（未实施）` | 讨论过、还没做 | 不用照做 |
| `快照（YYYY-MM-DD）` | 某个时点的审计或评估结果 | 只作对照，不作规范 |
| `历史（不具约束力）` | 旧版本留下来的意图 | 不要照着实现 |
| `索引` / `入口` | 目录页、导航页 | 以它指向的页面为准 |

「适用版本」写这份文档**据以核对**的版本，不是仓库当下版本；「最后核对」是你对着代码确认过内容仍成立的那天，不是改字体的那天。

版本号怎么动，只有三条规则：

| 情形 | 怎么写 |
| --- | --- |
| 要升到新版本 | 先把这份文档里的具体断言（数字、路径、类名、默认值）逐条对着代码核一遍，核完才改；改完顺手跑 `./tool/check.sh --docs` |
| 核不动（要真机、要外网、要跑起来才看得出） | 保持旧版本号，别为了整齐写新版本——那是没核对过的声明 |
| `历史（不具约束力）` 的旧稿 | 写 `适用版本 不适用（历史稿）`，它描述的版本已经没人装了 |
| `索引` / `入口` 页 | 随当前仓库版本走，因为它描述的是「现在有什么」 |

## 目录

满足任一条件就要 `## 目录`：

- 正文超过 120 行；
- H2 数量 ≥ 8；
- 页面是索引页（列出十几条链接）。

写法只用 H2 一层，锚点按 GitHub 规则（小写、空格转 `-`、去掉标点）：

```markdown
## 目录

- [为什么要有这一页](#为什么要有这一页)
- [页面骨架](#页面骨架)
```

不要手写序号（`1.`），标题里也不写序号——序号一改，目录和锚点全废。

## 标题层级

- 一份文档只有一个 H1，就是标题。
- 正文从 H2 开始，**不跳级**：H2 下面直接 H4 会让大纲断掉。
- H3 用于 H2 内部并列，H4 只在不进目录的细节里用。
- 标题要能单独读懂，不要写「其他」「补充」「说明」这种放进目录毫无信息量的词。

## 正文密度

**连续 ≥6 行非列表、非表格的正文就是文字墙**，读者会跳过它。拆法按内容选：

| 内容 | 写法 |
| --- | --- |
| 并列的若干条 | 无序列表，一条一个判断 |
| 有先后顺序的步骤 | 有序列表，一步一个动作 |
| 多对象、多字段 | 表格 |
| 因果/取舍论证 | 保留段落，但一段只说一件事，≤5 行 |
| 命令与输出 | 代码块 |

一段里出现「第一…第二…第三」且每项都带判断时，就是该拆成列表的信号。

## 表格

- 3 项以上、字段相同的列举用表格，不要用段落罗列。
- 表头写字段名，不写「项目」「说明」这类空话。
- 单元格里不要出现未转义的 `|`；需要时写 `\|`。
- 单元格尽量短；一行话超过两行显示就拆成小标题 + 列表。

## 代码块

- 每个代码块都标语言：`bash` / `dart` / `yaml` / `json` / `sql` / `ini` / `mermaid` / `text`。
- 没有语言的图、目录树、纯文本清单用 `text`。
- 命令块里只放能直接粘进终端的命令，不要混注释性叙述。
- 路径统一写仓库相对路径（`lib/...`），不写带 `file://` 前缀的本机绝对路径。

## 链接

- 站内一律相对路径：`[架构](architecture.md)`、`[约定](../AGENTS.md)`。
- 引用代码位置写成 `` `lib/app/app.dart:20` ``，不要做成链接——行号会漂。
- 指向实现文档的具体小节时带上章节名：`[验证](verification.md#门禁)`。
- 外链写完整 URL，不写「见这里」。

## 语言细节

- 中文与代码、英文、数字之间留一个空格：`用 Log.info 记录`、`窗口 900×600`。
- 句末用中文句号「。」，不要用英文句点结尾中文句子。
- 术语首次出现给出代码里的名字：`首个对象（`firstOrNull`）`。
- 不用感叹号，不用「非常」「十分重要」这类没有信息的修饰。
- 保留原文语气，不做「更好的表达」式改写——文档的职责是准，不是好听。

## 相关文档

每页末尾给 3–6 条「下一步去哪」：

```markdown
## 相关文档

- [架构](architecture.md) — 分层与依赖方向
- [数据模型](data-model.md) — 表、列与索引
```

链接写清楚「去看什么」，不要只写文件名。索引页与入口页可以省略这一节。

## 自检

改完文档跑：

```bash
python3 tool/check_docs.py            # 全仓
python3 tool/check_docs.py docs/x.md  # 指定文件
```

它会检查：H1 唯一、状态行存在且取值合法、长页有目录且锚点可达、标题不跳级、代码块都有语言、没有绝对路径、站内链接可达、表格列数一致、末尾有相关文档。门禁里已包含这一步。
