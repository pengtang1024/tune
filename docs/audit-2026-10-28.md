**审计日期：** 2026-10-28

**范围：** `lib/` 304 个文件 / 55,159 行；`test/` 117 个文件 / 23,775 行；`docs/` 与 `需求/` 全部；重点覆盖持久化、音乐库、音源、发现页、自动更新、启动链路。

## 一、维度 A：架构与数据流

### 🔴 A1. 淘汰会把收藏删掉

`app_database.dart:176-200`：

```sql
SELECT uri FROM (
  SELECT uri,
    ROW_NUMBER() OVER (
      PARTITION BY source_id
      ORDER BY pinned DESC, last_played DESC, play_count DESC,
               last_seen DESC, date_added DESC
    ) AS position
  FROM songs
  WHERE source_id != 'local'
)
WHERE position > ?
```

- `ORDER BY pinned DESC` 只是把收藏排到前面，**没有 `WHERE pinned = 0`**。
- 当某来源的收藏数超过「每来源最多保留」上限（例如收藏 600 首、上限 500），排名靠后的 100 首收藏会被 `position > limit` 删掉。
- 文档与设置文案都声明「收藏永不淘汰」，实现与声明相反。

**修复：** 在子查询加 `AND pinned = 0`，让 pinned 的行完全不参与排名；或对 `pinned = 1` 的行额外保留。

### 🔴 A2. 启动恢复队列失效（初始化时序）

`app.dart:44-46`：

```dart
Widget build(BuildContext context, WidgetRef ref) {
  ref.watch(playbackNotesProvider);          // 构建 PlaybackController
  final initialization = ref.watch(appInitializationProvider);
```

`playbackNotesProvider`（`playback_notes_provider.dart`）会 `ref.listen(playbackControllerProvider...)`，从而**在初始化完成前构建 PlaybackController**。`PlaybackController` 构造时 `_restoreSession` 调 `store.readSession()`：

```dart
PlaybackSession? readSession() => _session ?? _parseLegacy();
```

此时 `playbackSessionStore.init()` 还没跑（它在 `AppInitializer` 里），`_session` 为 null，旧 JSON 也已在迁移后改名为 `.migrated`，于是**队列与位置恢复为空**。

**修复：** 把 `ref.watch(playbackNotesProvider)` 移到 `initialization.when(data: ...)` 内，或在 `PlaybackNotesProvider` 里先 `await appInitializationProvider.future`。

### 🔴 A3. 窗口外收藏的 `pinned` 不会更新

`library_controller.dart:506-511` 的 `_pinnedUris()` 返回当前收藏；`save(songs, pinned:)` 只对**传入的窗口**写 `pinned`（`app_database.dart:120-168`）。

大库时 `songs` 只有 1000 首：用户在窗口外收藏一首歌（例如从搜索/播放器），它的 `pinned` 列不会更新；下一次 `prune` 可能把它当作未收藏删掉。

**修复：** `prune` 前单独执行 `UPDATE songs SET pinned = 1 WHERE uri IN (收藏)`（或 `pinned = CASE WHEN uri IN (...) THEN 1 ELSE 0 END`），不依赖 `save` 的窗口。

### 🟡 A4. 大库搜索/筛选/专辑只看第一窗

`library_state.dart` 的 `filteredSongs => filteredSongsOf(songs: songs, ...)`，而 `songs` 是窗口（≤1000）。`library_pane` 的专辑视图也基于 `songs`。

- 大库搜索「某首歌」时，如果它不在前 1000 首，**搜不到**。
- 来源筛选、专辑视图同样漏窗口外内容。

**修复：** 搜索/筛选/专辑查询下推 SQL（`WHERE title LIKE ?` / `GROUP BY album`），或在大库时把搜索切到独立的查询通道。

### 🟡 A5. `_markCopies` 只标记窗口

`library_controller.dart:101-112` 用 `state.valueOrNull?.songs`（窗口）标记副本。大库窗口外的已下载副本不会获得 `.tune` 标记，会与来源曲目重复显示。

**修复：** 标记改为按 URI 在 DB 里查，或分批处理全库。

### 🟢 A6. `dropSource` 后 `total`/`hasMore` 未重算

`library_controller.dart:346-366` 删除来源曲目后 `copyWith` 保留旧 `total`，统计与「加载更多」判断偏大。

## 二、维度 B：配置链路

### 🟡 B1. 五个 SQLite 连接写同一个文件

| 组件 | 打开位置 |
| --- | --- |
| `SqliteLibraryStorage` | `library_storage_io.dart:182-191` |
| `FavoritesStore` | `favorites_store.dart:32-40` |
| `PlaybackSessionStore` | `playback_session_store.dart:49-57` |
| `ListeningSignalStore` | `listening_signal_store.dart:42-50` |

四个 store 各自 `AppDatabase.open('library.db')`，加上 library 自己共 4–5 个连接。`busy_timeout = 5000` 只能缓解，不能消除写锁竞争；扫描保存与收藏/队列/收听写入并发时会阻塞 5 秒后失败。

**修复：** 用一个 `appDatabaseProvider`（`FutureProvider<AppDatabase>`）持有唯一连接，所有 store 注入同一个实例。

### 🟡 B2. 写放大：收藏/队列/收听每次全量重写

| 数据 | 写法 | 频率 |
| --- | --- | --- |
| 收藏 | `DELETE FROM favorites` + 全部 INSERT（`app_database.dart:298-318`） | 每次点击收藏 |
| 队列 | `DELETE FROM queue` + 全部 INSERT（`app_database.dart:337-357`） | 每次队列编辑（600ms 防抖） |
| 收听 | `DELETE FROM listening_signals` + 全部 INSERT（`app_database.dart:403-422`） | 每次播放结束/跳过 |

收藏几万、队列几千、收听 2000 时，每次写都是全表。SQLite 单事务能承受，但磁盘与锁开销随规模线性上升，与「百万级」目标矛盾。

**修复：** 改为增量 upsert（只写变化的 uri）+ 删除差异；`favorites` 用 `INSERT OR REPLACE`，队列用 position 差异更新。

### 🟡 B3. `prune` 的 `IN` 参数上限

`app_database.dart:197-198`：

```dart
final placeholders = List.filled(removed.length, '?').join(', ');
_db.execute('DELETE FROM songs WHERE uri IN ($placeholders)', removed);
```

SQLite 默认最多 999 个绑定参数（部分构建 32766）。一次 prune 删除 >999 行时抛 `too many SQL variables`，导致整次扫描失败。

**修复：** 用子查询直接删除（`DELETE FROM songs WHERE uri IN (SELECT uri FROM (...) WHERE position > ?)`），或分批 500 条删除。

### 🟡 B4. 单页超时叠加

`music_source_service.dart:464-488`：`pages` 循环里每页单独 `.timeout(adapter.scanTimeout)`，最多 10 页 × 90 秒 = 15 分钟。扫描 UI 只显示进度，没有总超时。

**修复：** 加总超时（如 `pages × scanTimeout` 或固定 3 分钟），或把 `pages` 上限降到 3–5。

### 🟢 B5. GitHub API 未认证限流

`update_service.dart:36-45` 直接请求 `api.github.com`，未带 token。共享 IP 下 60 次/小时，频繁检查会 403，用户看到「检查失败」。

**修复：** 缓存上次检查结果（如 6 小时），或提供可配置镜像。

### 🟢 B6. `RadioSourceAdapter` 对 SomaFM/RadioParadise 声明支持分页

`radio_source.dart` 的 `supportsPaging => true`，但 `SomaFmProvider`/`RadioParadiseProvider` 的 `fetch` 忽略 `offset`。点「加载更多」会重复请求同一批，靠去重后无新结果。

**修复：** 按 provider 判断是否可翻页，或对非 RadioBrowser provider 返回空。

## 三、维度 C：资源管理

### 🟡 C1. `installLinux` 删除备份过快

`update_service.dart:162-171`：换入新目录后立即 `_delete(backup)`。如果新版本启动失败（缺库、崩溃），用户没有 `.tune-previous` 可回退。

**修复：** 保留上一版本备份，或延迟到新版本成功启动一次后再删。

### 🟡 C2. `restart` 直接 `exit(0)`

`update_service.dart:175-179` 启动新进程后立刻 `exit(0)`，没有等待 `PlaybackSessionStore` 的 5 秒位置节流写入，可能丢最后几秒位置。

**修复：** 重启前触发一次同步保存。

### 🟢 C3. DB 打开失败无降级

`SqliteLibraryStorage._db()` 抛异常时 `load()` 返回空、`save()` 静默失败；`FavoritesStore.init()` catch 后 `read()` 回退 JSON（空）。用户会看到「库空了」而没有提示。

**修复：** 初始化失败时在界面给出明确错误，而不是静默空库。

## 九、架构判断

- 分层（presentation → application → domain/data）没有被破坏；音源注册表、库控制器、发现控制器的职责边界清楚。
- SQLite + 分页 + 数据库端淘汰的方向正确，问题集中在**窗口语义与全库语义混用**（A3、A4、A5）和**多连接/全量写**（B1、B2）。
- 最大风险不是性能，而是「收藏被淘汰」和「启动丢队列」这两个用户可直接感知的数据问题。
