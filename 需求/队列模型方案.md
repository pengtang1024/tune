# 队列模型方案

## 1. 现状

播放队列目前由 `PlaybackState` 的三个字段描述（`lib/features/player/domain/playback_state.dart`）：

```dart
final Song? currentSong;   // 当前曲目
final List<Song> queue;     // 队列
final int currentIndex;     // 游标（下标）
```

行为规则散落在 `PlaybackController`（`lib/features/player/application/playback_controller.dart`）：

| 场景 | 现在的实现 |
| --- | --- |
| 下一首（顺序） | `(currentIndex + 1) % queue.length` |
| 下一首（随机） | `_randomIndex(excluding: currentIndex)`，每次现场摇一个下标 |
| 上一首 | 顺序：`(currentIndex - 1 + length) % length`；随机：同下一首，也是摇随机 |
| 单曲循环 | `_handleCompletion` 里 `_startAt(currentIndex)` 重播当前曲目 |
| 队列编辑 | `addToQueue` / `removeFromQueue` / `reorderQueue` / `clearQueue` / `playAt` |

## 2. 问题

### 2.1 游标是下标，队列编辑全靠手工修补（P0）

下标只是「位置」，不是「身份」。只要队列被改动，下标就可能失效，于是每一处队列操作
都要自己把下标修回来：

- `removeFromQueue`：删掉当前曲目之前的条目后要 `currentIndex - 1`（`playback_controller.dart:353`）。
- `reorderQueue`：拖拽之后不知道当前曲目跑到哪了，只能用
  `queue.indexWhere((song) => song.uri == currentUri)` 反查（`:396`）。

这两处是给「下标当游标」打的补丁。以后再加「插入到下一首」「跨来源合并」「去重」，
只会把同样的修补再抄一遍，改动面越大越容易漏。

### 2.2 随机不是真随机（P0）

随机模式只在 `next()` 那一刻摇一个下标，**队列本身没有被打乱**。后果：

- 界面显示的顺序 ≠ 实际播放顺序，用户看不到「接下来放什么」。
- 随机模式的 `previous()` 也是摇随机，名字叫「上一首」却跳到不相干的一首。
- 随机模式下同一首可能被反复抽到（一轮里能听到同一首好几次）。

### 2.3 「上一首」不是「刚播过的那首」（P1）

顺序模式的 `previous()` 回的是**队列里的前一项**，不是**刚才播过的那首**。用户跳着听之后
（`playAt`、删掉当前曲目自动切歌），上一首基本没有意义。模型里没有任何历史。

### 2.4 同一事实存了两份（P1）

`currentSong` 与 `queue[currentIndex]` 描述同一件事，没有一行代码保证两者一致，
全靠每次操作手写对齐（`addToQueue` 在空队列时同时写 `currentSong: queue.first` 和
`currentIndex: 0`，靠巧合一致）。

### 2.5 预取在随机模式下基本失准（P1）

`TrackPrefetcher` 预取的是「队列顺序的下一首」。随机模式下真实下一首是摇出来的，
命中率只有 1/(N-1)，预取基本白干。根因还是 2.2：队列不是播放顺序。

## 3. 模型

### 3.1 状态结构

```dart
class PlaybackState {
  /// 队列即播放顺序：列表的顺序就是播放的顺序。
  final List<Song> queue;

  /// 游标：当前曲目的身份，不是下标。
  ///
  /// 下标由队列推导，队列增删重排之后游标自动跟随，
  /// 不需要任何一处手工修补下标。
  final String? currentUri;

  /// 播放历史：最近播过的曲目身份，最近的排在最后。
  final List<String> history;

  /// 播放模式。UI 依赖这个字段，语义见第 4 节。
  final PlayMode playMode;
}
```

要点：

- **游标是身份（uri）**：`Song.uri` 是这个工程里唯一的曲目身份（去重、
  缓存文件名、地址刷新都用它），游标沿用它。
- **队列里 uri 唯一**：`addToQueue` 已经按 uri 去重；`playQueue` 也要去重，
  否则同一首出现两次时游标会有歧义。去重时保留第一次出现的位置，
  起始曲目按「原始下标 ≥ `startIndex` 的第一首」重新定位；
  `startIndex` 越界仍然沿用现状（播最后一首）。
- **`history` 存 uri 而不是 Song**：历史里的曲目可能已被移出队列，
  用 uri 存可以在播放时判断它是否还在；顺带避免历史钉住旧的 Song 对象。

### 3.2 派生量

```dart
/// 当前曲目在队列里的位置；不在队列里时为 -1。
int get currentIndex =>
    currentUri == null ? -1 : queue.indexWhere((song) => song.uri == currentUri);

/// 当前曲目。
Song? get currentSong {
  final index = currentIndex;
  return index < 0 ? null : queue[index];
}
```

`currentSong` 与 `currentIndex` 从此只有一个出处（队列 + 游标），不可能再分叉。
`currentIndex` 仍然是队列长度级别的小扫描，UI 每次读一次，可以接受。

### 3.3 队列即播放顺序

不再单独维护一份「播放排列」。队列列表的顺序就是播放顺序，于是：

- 界面所见即所播，随机模式下也不需要额外状态。
- 拖拽重排立刻改变播放顺序（这本来就是用户的直觉）。
- `TrackPrefetcher` 取「队列里的下一首」在随机模式下也准了 → **预取规则不用改**。

### 3.4 随机：一次重排

- 切到随机：对队列做一次 Fisher–Yates 重排。当前曲目继续播放，高亮（派生下标）
  自动跟到新位置。
- 切回顺序：恢复打乱前的顺序。控制器在重排前记一份 uri 快照；
  随机期间队列一旦被编辑（增删或拖拽），快照就作废，保持用户给的顺序，
  避免复活已删除的曲目。
- 队列只有一个曲目时重排没有意义，原样保留。

由此，随机模式的行为从「每次现场摇一首」变成「重排后按序播一轮」：
一轮内不重复，界面可见，下一首可预知。

### 3.5 上一首与历史

- 切歌时（`next()`、`playAt()`、播完自动切歌、删掉当前曲目后的自动切歌）
  把上一首的 uri 压入 `history`，上限 50 条。
- `previous()`：`history` 非空 → 弹出最后一首并播放它；`history` 为空 →
  回退到队列的前一项（`(index - 1 + length) % length`）。
  随机模式下队列即播放顺序，同一个公式同样成立。
- 走历史的那一步会**消费**这条记录，不再把当前曲目压回去：连按上一首会一路
  往回走，不会来回弹；走队列的那一步同样不记历史，否则顺序播放时上一首
  只能在两首之间来回。
- `playQueue`（换队列）→ 清空 `history`。

### 3.7 顺序播放不受影响

随机是队列重排，顺序播放是这套模型里最老的一档，必须一点不变：

- **下一首**：`next()` 不再按模式分支，公式始终是 `(index + 1) % length`，
  与重构前逐字相同；顺序模式走到末尾照旧回到第一首。
- **上一首**：优先走历史，历史为空时回到 `(index - 1 + length) % length`。
  顺序播放时历史与队列顺序一致，所以连按上一首的结果与重构前相同
  （一路往回走，不会只在两首之间弹）。
- **唯一的差别**：跳播之后「上一首」回到跳之前那一首，而不是队列里的前一项。
  这正是本方案要修的问题。
- **随机的副作用是临时的**：切换到随机时才重排队列一次；切回顺序时恢复重排前的
  顺序（期间编辑过队列才不恢复）。顺序模式播放的永远是队列里那条顺序。
- 回归测试：`test/app/playback_controller_test.dart` 的 `sequential playback` 组
  把上面几条钉住。

### 3.8 与缓存、预取的关系

- 预取目标：队列中的下一首。队列即播放顺序 → 随机模式下也准。
- 单曲循环不预取（当前曲目本来就在缓存里）。
- 其它规则（同时只预取一首、队列走开后停掉过时预取）不变。

### 3.9 队列的内容从哪来

队列里放什么，只由用户的显式动作决定；**音乐库的那一屏列表不是队列**。

- **单击音乐库里的一首** → 默认把这首排进队列并立即播放，队列里已有的曲目
  原地保留。音乐库动辄几千首，点一下就把整张列表塞进队列，队列页当场变得
  没法看，随机和预取也在几千首里打转。想要「只听这一首」时，在设置里打开
  「单击歌曲时替换播放队列」。
- **整列表批量入队** → 音乐库页头的「把整个列表加入队列」图标按钮，
  一次把当前可见的曲目排进队列（已在队列里的跳过），返回新增条数。
- **单曲入队** → 曲目行尾的「加入队列」按钮。
- **双击列表里的一首** → 默认照旧入队并立即播放，同时把这首标成喜欢；设置里
  打开「双击时只标成喜欢」后，双击只加红心，正在放的曲子不动。双击只负责加，
  不取消喜欢；取消喜欢用行尾红心单击。
- **在线搜索结果** → 默认点中的这一首排进队列并立即播放；替换模式下整批
  播放。搜索结果本身就是一个有界上下文，它是用户当下的检索范围，
  不是「碰巧在看的那一屏」。

## 4. 行为规则表

| 操作 | 结果 |
| --- | --- |
| 顺序模式下一首 | 队列的下一项，到末尾回到第一项 |
| 随机模式下一首 | 同上（队列已被重排过） |
| 单曲循环 | 播完重播当前曲目，不前进、不预取 |
| 主动按「下一首」（任何模式） | 始终前进到队列下一项；单曲循环只在**播完自动切歌**时重播当前曲目 |
| 上一首 | 优先回放刚播过的那首；没有历史时回到队列的前一项 |
| 切到随机 | 队列重排一次，当前曲目继续播，高亮跟随 |
| 切回顺序 | 恢复重排前的顺序（期间编辑过队列则不恢复） |
| 删除当前曲目 | 自动切到原来位置的下一首；没有下一首则切到最后一首；队列空则清空 |
| 删除当前曲目之前的条目 | 当前曲目不变，高亮自动前移 |
| 拖拽重排 | 当前曲目不变，高亮自动跟随 |
| 点播队列中的某首 | 播放该首，并把原来的当前曲目压入历史 |
| 换队列（`playQueue`） | 队列整体替换，清空历史 |
| 点音乐库的一首 | 默认排进队列并立即播放，队列里已有的曲目保留；替换模式下队列整体换成这一首（历史清空） |
| 双击列表里的一首 | 默认照旧入队并立即播放，同时切换这首的喜欢状态；打开「双击时只标成喜欢」后只加红心，队列与播放都不动 |
| 整列表加入队列 | 一次把可见曲目全部排进队列，已在队列里的跳过，返回新增条数 |
| 清空队列 | 停止播放，队列与历史清空 |

## 5. 迁移步骤

每一步都可以单独验证，前一步绿灯再做下一步。

1. **状态层**（`lib/features/player/domain/playback_state.dart`）
   - 字段换成 `queue` + `currentUri` + `history`；
   - `currentSong` / `currentIndex` 变成派生 getter；
   - `copyWith` 同步调整。
2. **控制器**（`lib/features/player/application/playback_controller.dart`）
   - 所有对 `state.currentSong` / `state.currentIndex` 的**写入**改成写 `currentUri`；
   - 队列方法重写：`playQueue`（含 uri 去重）、`addToQueue`、`removeFromQueue`、
     `reorderQueue`、`clearQueue`、`playAt`；
   - `next()` / `previous()` 按第 4 节规则实现；
   - `cyclePlayMode()` 实现随机重排与恢复。
3. **预取**（`lib/features/player/application/track_prefetcher.dart`）
   - 规则不变（队列即播放顺序后，随机模式也准）。
4. **UI**：**零改动**。`state.queue` 仍是 `List<Song>`，`currentSong` / `currentIndex`
   仍是可读属性，`playMode` 仍在。队列页、正在播放页、左栏播放器都不用动。
5. **测试**：队列状态只被 `test/app/playback_controller_test.dart` 引用（10 处），
   其它测试不碰队列，改动面可控。
6. **文档**：更新 [紧凑播放器重构方案](紧凑播放器重构方案.md) 里
   「重复/随机语义」一节，指向本文。

## 6. 测试清单

放在 `test/app/playback_controller_test.dart`：

- 队列里的当前曲目以身份标识：删除它前面的条目后，当前曲目不变、高亮前移。
- 拖拽重排后当前曲目高亮自动跟随。
- 删除当前曲目后自动切到下一首并继续播放；删的是最后一首时切到新的最后一首。
- 随机模式会重排队列，队列顺序即播放顺序，当前曲目高亮跟随。
- 切回顺序模式恢复重排前的顺序。
- 随机期间编辑过队列就不恢复旧顺序。
- 上一首回到刚播过的那首；历史为空时回到队列的前一项。
- 换队列后历史清空。
- 队列里同一首曲目只出现一次（`playQueue` 去重）。
- 随机模式下预取的目标就是队列里的下一首。
- 顺序播放回归：下一首走到末尾回到第一首；上一首从第一首回到最后一首；
  连按上一首一路往回走不弹跳；随机来回一轮后队列顺序照旧。
- 队列来源：单击音乐库的一首 → 这一首排进队列并立即播放，队列里已有的曲目
  保留（替换模式下队列只有这一首）；整列表入队 → 队列是整张
  可见列表；重复的曲目不重复入队。
- 双击列表里的一首 → 默认照旧入队并立即播放并标成喜欢；打开「双击时只标成喜欢」后只加红心，不打断正在放的曲子。

## 7. 已知取舍与后续

- **随机模式行为变化**：从「每次摇一首」改成「重排后按序播一轮」。一轮内不重复，
  界面可见，下一首可预知；这是本方案的核心收益。
- **历史只在内存**：退出应用即丢，v1 不做持久化（也不做保存式歌单）。
- **不做「不重复（播完就停）」**：现有三种模式已覆盖需求，其余模式后续再说。
- **播放模式仍是一个 enum**：`顺序/单曲/随机` 三态保留，因为 UI 只有一个模式按钮。
  「随机 + 单曲循环」这类正交组合本轮不做。
- 队列仍不持久化：会话队列，重启即空（与 [紧凑播放器重构方案](紧凑播放器重构方案.md) 的结论一致）。
