# 🌍 多语言设计规范

多语言设计是产品全球化过程中的核心环节，旨在通过视觉、交互和内容适配，让不同语言背景的用户获得一致且流畅的体验。它不仅涉及 "翻译"，更需要从设计逻辑、文化适配、技术实现等多维度系统性规划。以下从核心原则、设计要点、文化适配和技术支持四个方面展开说明：

## 🎯 一、多语言设计的核心原则

### 🔗 一致性优先
无论语言如何切换，产品的核心功能入口、交互逻辑、视觉层级需保持一致，避免用户因语言变化产生认知混乱。例如：按钮位置、导航结构、图标含义在各语言版本中需统一。

### 🧘 灵活性适配
不同语言的文字长度、排版规则、阅读习惯差异极大（如英语→德语长度可能增加 30%，阿拉伯语是右到左书写），设计需预留弹性空间，避免 "硬编码" 式固定布局。

### 🌏 文化无歧义
颜色、图标、符号、隐喻需规避文化禁忌，确保视觉元素在目标语言地区的含义与产品意图一致（如 "绿色" 在多数地区代表 "安全"，但在部分中东文化中可能与宗教禁忌相关）。

### ⚖️ 优先级分层
核心信息（如功能名称、操作提示）需保证清晰度和易读性，次要信息（如说明文本）可适当优化排版，但需避免信息丢失。

## 🎨 二、关键设计要点

### 📝 1. 文本布局：应对 "长度差" 与 "排版差"

#### 预留长度空间
不同语言的文字长度差异显著：英语→西班牙语约增加 20%，英语→德语约增加 30%，英语→俄语约增加 40%，而中文、日语等东亚语言长度相对稳定。设计时需按 "最长语言" 预留空间，例如：
- 按钮、标题区域采用弹性宽度，避免固定像素值
- 文本容器设置 "最大宽度" 而非 "固定宽度"，允许换行但不挤压内容
- 移动端可通过 "折叠 / 展开""横向滚动" 处理超长文本（如标签栏、菜单选项）

#### 适配排版规则
书写方向：多数语言是左到右（LTR），但阿拉伯语、希伯来语等是右到左（RTL），设计需支持 "镜像布局"—— 不仅文本方向反转，界面元素（如按钮位置、图标方向）也需同步适配（例如返回按钮在 RTL 语言中应靠右）。

字符特性：中文、日文等无空格分隔，需避免过窄容器导致文字挤压；泰语、越南语有复杂声调符号，需保证字体行高足够，避免符号被截断。

断句逻辑：英语依赖空格断词，中文需按语义断句，设计时需避免强制截断（如中间加 "…"）破坏语义，可通过动态调整字号、换行策略优化。

### 🔠 2. 字体选择：兼顾可读性与文化适配

#### 跨语言字体兼容性
优先选择支持多语言字符集的字体（如 Noto Sans、Roboto、思源黑体），避免因字体缺失导致文字显示为 "□" 或乱码。

#### 语言特性适配
- 中文：需保证笔画清晰，避免过细字体在小尺寸下模糊（如标题用粗体，正文用常规体）
- 英文：区分衬线（Serif）与无衬线（Sans-Serif），正文优先无衬线字体提升屏幕可读性
- 阿拉伯语：字体需支持连笔特性，避免字符断开导致阅读困难

### 🎛️ 3. 交互设计：降低语言切换成本

#### 语言切换入口明确化
将语言选择放在高频访问位置（如设置页顶部、个人中心入口），避免隐藏过深；切换后需保留用户当前页面状态（如购物车内容、表单填写进度），减少重复操作。

#### 提示信息 "去语言依赖"
关键操作提示（如 "提交成功""网络错误"）可结合图标 + 文字双重传递信息，降低纯文字理解压力（例如成功用✅，错误用❌，配合简短文本）。

## 🌐 三、文化适配：避免 "翻译正确但体验错位"

### 🖼️ 符号与图标本地化
避免使用具有文化特异性的符号：
- 手势："OK" 手势在巴西、土耳其等国可能被视为冒犯
- 动物：猫头鹰在西方代表 "智慧"，但在印度部分地区被视为 "不吉利"
- 颜色：红色在中文文化中象征 "喜庆"，在南非可能与哀悼相关，在德国需谨慎使用（避免与纳粹符号关联）

### 📝 内容风格适配
不同语言的表达习惯差异需体现在文案风格中：
- 英语偏向简洁直接，中文可适当增加礼貌性词汇（如 "请""您"）
- 日语重视谦逊表达，需使用敬语体系
- 阿拉伯语文案可能更强调情感共鸣，需避免过于生硬的指令式表达

### 📅 格式本地化
日期、时间、货币、计量单位需按目标地区习惯显示：
- 日期：美国 "MM/DD/YYYY" vs 中国 "YYYY/MM/DD" vs 欧洲 "DD/MM/YYYY"
- 货币：美元 "$100" vs 欧元 "100 €" vs 人民币 "¥100"（符号位置、货币代码是否显示需适配）
- 数字分隔：英语用 "," 分隔千位（1,000），部分欧洲语言用 "."（1.000）

## ⚙️ 四、技术支持：让设计落地更顺畅

### 🌐 国际化框架（i18n）整合
设计需与开发协作，采用支持多语言的技术框架（如前端用 React-i18next、Vue-i18n），将文本内容与代码分离存储（如通过 JSON 文件管理多语言文案），避免硬编码导致的修改成本过高。

### 📐 响应式与动态布局技术
利用 CSS 的min-width max-width、弹性布局（Flex）、网格布局（Grid）等技术，确保文本长度变化时界面不崩坏；对 RTL 语言，可通过direction: rtl自动反转布局，减少手动调整成本。

### 🧪 测试与迭代
上线前需通过 "本地化测试" 验证效果：
- 检查文本是否溢出、截断或重叠
- 邀请目标语言用户体验，收集 "语义歧义""操作困惑" 等反馈
- 针对高频问题（如某语言版本按钮文字过长）建立快速迭代机制

### 🏆 案例参考：优秀多语言设计实践
- 苹果官网：支持 40 + 语言，通过弹性布局适配文字长度，RTL 语言版本完全镜像，且保持视觉统一性
- 谷歌产品：文案简洁且风格适配地区文化，图标采用 "极简符号"（如搜索、设置）规避文化歧义
- 微信国际版（WeChat）：针对英语用户简化功能名称（如 "朋友圈"→"Moments"），调整日期格式为当地习惯

## 🏁 总结

多语言设计的本质是 "以用户为中心" 的全球化延伸 —— 它要求设计师跳出单一语言视角，通过灵活的布局、文化敏感的视觉符号和技术协同，让产品在不同语言环境中既 "好用" 又 "易懂"，最终实现 "跨越语言，但不跨越体验" 的目标。

## 🛠️ 五、Tune 的落地实现

上面的原则在 Tune 里对应下面这些具体做法。

### 语言清单

| 语言 | 代码 | 说明 |
| --- | --- | --- |
| 简体中文 | `zh_CN` | 模板语言，界面默认 |
| 繁體中文 | `zh_TW` | 独立翻译，不做简繁转换 |
| 中文（通用） | `zh` | 跟随系统的通用中文 |
| English | `en` | |

- **当前只做中英文**。中文的三种写法（简体、繁體、通用）加上英文，
  先把这四种做到精确、完整，再考虑别的语言。
- 语言列表由 `AppLocalizations.supportedLocales` 派生，新增语言只需要加一份 ARB，
  不需要改设置页的代码。
- 语言名用**该语言自己的写法**（endonym）显示：繁體中文、简体中文、English……
  读者一眼就能找到自己的语言。
- 以后要加一种语言：放一份 `lib/l10n/app_<locale>.arb`，
  在 `locale_labels.dart` 里补上它的 endonym，执行 `flutter gen-l10n`。
  质量门禁会检查它有没有漏掉任何一条文案。
- **项目文档同样只做中英文**（`README.md` 与 `README_en.md`），
  文档站的语言也是 `zh-CN`。


### 文案与代码分离

- 文案全部放在 `lib/l10n/app_<locale>.arb`，用 `flutter gen-l10n` 生成
  `app_localizations*.dart`；代码只用 `context.loc.xxx` 或
  `AppStrings.instance.xxx`。
- 界面与数据层不允许出现中文字面量，测试会扫描 `lib/data`、`lib/core`、
  `lib/features`、`lib/shared` 与 `lib/app`。
- 新增文案时所有语言一起补齐，缺一个语言测试就会失败。

### 一份文案只写一次

目录里的文案按**概念**组织，不按界面组织，也不按音源组织。

- 同一个概念只留一条 key。侧边栏的「音乐库」、音乐库页面的标题与设置卡片
  读的是同一条 `libraryTitle`，不是三条长得一样的文案。
- 描述**字段种类**的文案是共享的：搜索关键词、每次扫描数量、服务器地址、
  用户名、密码、音质各只有一条（`fieldQuery`、`fieldLimit`、`fieldServer`……
 ），不管有多少个音源在用。
- 描述**数字**的文案把数字带上：`fieldLimitHint(count, max)` 一条就够，
  每个音源把自己的上下限传进来，不再各写一句「默认 20，最大 50」。
- 只有真正属于某个音源的说法才留在音源名下：它的 API 地址、它的订阅地址、
  它独有的错误提示。
- 结果是**新增一个音源不用再写十几条文案**，通常一条都不用写。


### 随语言变化的内容

界面上的文字有两种：一种跟着语言走，一种天生只有一个样子。

- **跟语言走的**（按钮、标题、字段名、错误提示……）一律进 ARB。
- **天生只有一个样子的**是服务与品牌的名字：Jamendo、Subsonic、
  Wikimedia Commons、SomaFM…… 这些是专有名词，所有语言写法相同，
  翻译反而会让用户搜不到。
- **音源的名字与描述**由目录给出。目录不是常量，而是**翻译的函数**：
  `BuiltInMusicSources.of(strings)` 按一份翻译写出 13 个内置实例的名字与描述，
  所以它永远回答"当前语言"里的名字，不会把第一次调用时的语言一直记着。
- **界面显示音源名时读的是界面正在用的那份翻译**（`context.loc`），
  不是某个全局变量。于是切换语言后音乐库、播放队列、正在播放页上的
  来源名会立刻跟着变，界面也一定会重画。
- **切换语言时 `AppStrings` 立刻换**（`SettingsController.setLocale`），
  不等下一帧，服务层读到的也是新语言。


### 音源的两个名字

品牌名不翻译，但读者仍要知道那是个什么音源。于是每个音源有两个名字：

- **品牌名**是音源自己写的名字（`Openverse`、`Jamendo`）——它是标识，
  读者靠它认出这是哪个服务；
- **本地化名**是这个音源在读者语言里的名字（`开放版权聚合`、`独立音乐曲库`），
  它说明这是什么。

名字本来就在读者语言里的音源（本地音乐、播客订阅、网络电台）没有第二个
名字，只写一个。

两个名字不写进 chip 的正文：chip 只画一个**固定大小的图标**，图标不随名字
长短变形，一行曲子的宽窄不再被音源名字牵着走。两个名字写在 tooltip 里
（`Openverse · 开放版权聚合`），详情面板的「来源」那条事实也把它们写全。

本地化名不能是品牌名的翻译：`互联网档案馆`、`维基共享资源`、`苹果音乐试听`
都是把品牌名翻了一遍，写在 chip 里等于把同一句话说两遍；`苹果音乐试听`还把
iTunes 说成了另一个服务。本地化名要说明这个音源是干什么的：`公共领域音频`、
`商店试听片段`、`自由授权媒体`。描述里提到品牌时用品牌自己的拼法
（`Internet Archive 的开放音频收藏`），不写中文版。

### 类型名与实例名

音源是「类型 + 实例」：类型是代码里的适配器，实例是读者的一条配置。

- **类型名**跟着类型走：所有 Jamendo 实例都叫 Jamendo，图标也是 Jamendo 的图标。
  内置实例的名字由目录给出，切语言时跟着目录一起换。
- **实例名**是读者起的：读者可以给第二个 Jamendo 起名（「深夜爵士」），
  起了名就用它，界面不再拿类型名盖掉它。
- 读者起的名字不进翻译——它本来就是读者写的字，翻译目录里没有它的位置。

### 语法与格式

- 计数类文案用 ICU 复数（`{count, plural, =1{...} other{...}}`），
  英语按 "1 song / 2 songs" 区分，中文保持简单形式。
- 计数的数字用 ARB 的 `format: "decimalPattern"` 交给 `intl` 按当前语言分组，
  1234 首写作 "1,234 首"，而不是手写分隔符。
- 日期与时间用 `DateFormat` 按当前语言格式化，而不是手写 `HH:mm`：
  英文是 `2:30 PM`，中文是 `下午 2:30`，日期顺序也跟随当地习惯。
- 音源设置里的固定取值（音质、电台目录）用数据层声明的选项渲染成下拉框，
  选项文字同样走多语言目录。
- **中文用全角标点**：`播放失败：{error}` 里的冒号是全角的，中文与
  拉丁字母之间留一个空格。
- **排序按语言来**：标题排序忽略大小写与重音（`compareText`），
  "Ärger" 排在 "Apfel" 后面，而不是被丢到所有 "Z" 开头的标题之后；
  没有字母表的文字（中日韩、西里尔）保持自己的字符顺序。

### 质量门禁

`test/app/localization_test.dart` 守住六条底线：

1. 所有语言拥有相同的 key 集合；
2. 每种语言展示自己的文案（生成代码里必须能找到该语言 ARB 里的文字），
   防止某个语言悄悄回退到模板语言；
3. 代码里引用的 key 都在目录中声明过；
4. 某种语言里不出现别的语言的文字，例如英文里不能混进汉字；
5. 界面里没有硬编码的中文；
6. **界面里没有硬编码的拉丁文字**：只检查读者看得见的位置（文本组件与
   组件的具名参数），日志、键名、地址不算；服务与品牌的专有名词在白名单里。

`test/app/localization_numbers_test.dart` 检查数字真的按语言分组，
`test/app/localization_test.dart` 则同步认识带格式的占位符，
生成代码里 `count` 会变成 `countString`。

`test/app/localization_sources_test.dart` 检查音源的名字与描述真的跟着
语言走，并检查**所有音源共用同一套字段文案**：每个音源的字段名必须出自
共享的那几条，扫描数量的提示必须写着这个音源真正在用的上下限。
`test/core/text_order_test.dart` 检查排序忽略大小写与重音。

### 门禁之二：把界面画出来看

`test/app/localization_render_test.dart` 不读目录，它**把每一页画出来**，
再从画好的树上把读者看得见的字读下来：中英文各画一遍，于是它能发现
目录看不见的三件事：

1. **界面上出现目录里没有的字**：文字组件、提示气泡、输入框里的提示，
   凡是读者能看到的都算；
2. **两种语言混在一起**：英文界面里不能出现汉字，中文界面里不能出现
   没有翻译的英文（品牌名、服务的名字、数字、时长、版本、路径除外）；
3. **字太长放不下**：英文的标签比中文长，按中文排的版会把英文挤出去。
   门禁要求两种语言下每一页都不溢出。

画的是两种尺寸：桌面上的大窗口（1400×900）与挤在一处的窄窗口
（760×483）。窄窗口放不下的英文标签，在大窗口下看不出来。

画的不只是页面，还有盖在页面上的窗口：在线搜索的浮层、音源的设置对话框、
一首歌的详情浮层，以及在线搜索的结果（结果按音源分组，每组都写着音源的
名字）。这些窗口里的字同样是读者看得见的字。

每一页画在自己的导航器上（`MaterialApp` 带 key），这样上一页没关掉的
窗口（搜索的浮层、音源的对话框）不会伸到下一页去挡住它的按钮——
浮层留下的遮罩会挡住下一次点击，而"点不到"在测试里长得跟"没画出来"
一模一样。

界面的字有两个来源，缺一不可：`context.loc`（界面自己）与
`AppStrings.instance`（数据层）。数据层的那一份跟着语言走，靠
`SettingsController` 在读出语言时就把它设好——不等第一帧画出来，
这样启动扫描的报错也是用户选的那种语言。
