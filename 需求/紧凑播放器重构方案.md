# Tune 紧凑播放器重构方案

> 目标：把当前「多页面 + 大侧栏 + 营销式首页」的音乐播放器，收敛为一套 **900×600 紧凑桌面、以播放为核心** 的产品与代码架构。
>
> 本文是实施方案，不代表已经完成。现有未提交修改不回退，采用「新壳层先跑通、旧 UI 后清理」的渐进式迁移。

---

## 0. 总原则：架构优化优先于代码优化

这条原则高于本方案中的所有局部实现细节，后续任何改造都必须先满足它。

1. **先定边界，再写代码**：先确认「谁拥有状态、谁可以调用谁、数据往哪个方向流」，再讨论组件拆分、命名、抽取和性能微调。
2. **先修数据流，再修 UI**：页面溢出、状态不同步、重复刷新，优先检查状态来源和依赖方向；不要用 `setState`、post-frame、`Future.delayed` 或布局补丁掩盖架构问题。
3. **单一事实来源**：播放状态只能有一个来源（`PlaybackController`），音乐库、队列、设置各自只有一个 controller；禁止同一份数据在两个 provider 里各存一份。
4. **依赖单向**：UI → controller → service → data。`data/`、`domain/` 不依赖 `features/`；`library` 不依赖 `player` 的 UI；`player` 不依赖 `library` 的 UI。
5. **不做「为了兼容错误架构」的代码优化**：如果一个组件需要大量判空、post-frame、重复状态同步才能工作，先拆边界或换归属，而不是继续加 if。
6. **局部性能优化让位于结构正确**：`const`、`RepaintBoundary`、缓存、`select` 等优化必须建立在正确的状态边界之上；结构错误时，性能优化只会让问题更隐蔽。
7. **迁移优先于重写**：新链路先可用，旧链路后删除；每一步保持可编译、可运行、可回滚。

> 判断一次改动是否合格，先问三个问题：
> 1. 这次改动是否让职责更单一？
> 2. 是否减少了跨层依赖或重复状态？
> 3. 如果以后要加一个平台/页面，是否只需要接一个新入口，而不是改一圈旧代码？
>
> 如果三个答案都是否，即使代码更短、更快，也不应作为主要优化方向。

## 1. 结论先行

### 1.1 产品形态

采用 **双栏常驻布局**，不做首页、不做大侧栏、不做底部迷你播放器：

```
┌──────────────────────────────────────────────────────────────┐
│  Tune                                            ⚙          │ 44
├──────────────────────────────┬───────────────────────────────┤
│                              │  音乐库        播放队列        │
│         专辑封面              │  ┌─────────────────────────┐  │
│          216×216             │  │ 🔍 搜索歌曲             │  │
│                              │  ├─────────────────────────┤  │
│        歌曲标题               │  │ ▶ 歌曲 A   歌手   3:21  │  │
│      歌手 · 专辑              │  │   歌曲 B   歌手   4:02  │  │
│                              │  │   歌曲 C   歌手   2:58  │  │
│   ───────●──────────  1:24   │  │   ...                   │  │
│                      3:45    │  │                         │  │
│                              │  │                         │  │
│    ⏮    ▶     ⏭    🔁        │  │                         │  │
│    🔊 ───────────────        │  │                         │  │
└──────────────────────────────┴───────────────────────────────┘
        左栏：播放器（常驻）              右栏：内容区
```

- **左栏常驻播放器**：封面、歌曲信息、进度、上一首/播放/下一首、循环模式、音量。
- **右栏三块内容**：音乐库（默认）、播放队列、设置。音乐库与队列用顶部页签切换，设置由右上角齿轮进入。
- **打开即用**：启动后右栏直接显示音乐库；有歌可播时左栏立即可控，没有歌曲时显示空状态与「扫描音乐」入口。
- **低频功能全部退出主界面**：首页 Hero、通知中心、歌词、睡眠定时、均衡器、播放历史、账户资料、桌面歌词、开机启动、字体大小等不进入 v1 主路径。
- **后台播放与默认播放器单独立项**：MPRIS 系统媒体控制、系统托盘常驻、默认播放器这三条能力按 [桌面集成方案](桌面集成方案.md) 交付，不塞进上面这条主路径。

### 1.2 架构形态

- **表现层按 feature 聚合**：`player / library / queue / settings / shell` 各自拥有 state、controller、widgets。
- **单向数据流**：Widget → Controller → Service；Service 不依赖 UI，Library 不依赖 Player UI。
- **播放队列进入状态**：队列不再是 `PlaylistService` 里的可变私有字段，而是 `PlaybackState` 的一部分，任何增删改都会触发 UI 刷新。
- **删除全局耦合**：移除 `AppBarState`、`MenuState`、`ResponsiveContext`、路由观察者同步标题等为「多页面/多端」设计但当前不再需要的机制。
- **新老并存，分阶段替换**：新代码放 `lib/app` 与 `lib/features`；新链路验收后旧 `lib/ui` 已整批删除。

## 2. 重构前的现状问题（为什么需要架构调整）

| 问题 | 证据 | 影响 |
|---|---|---|
| 默认窗口过大 | `PlatformConstants` 1280×720；`linux/runner/my_application.cc` 1280×720 | 900×600 下旧页面必然拥挤 |
| 布局层级过重 | `DesktopLayout` 220px 侧栏 + 48px AppBar + 64px MiniPlayer + 16px 外边距 | 900 宽时内容区仅约 580px，高度不足 480px |
| 页面与导航冗余 | 4 个主页面 + 搜索/通知/扫描/历史等路由；3 套响应式壳层；菜单状态 + 路由观察者两套导航同步 | 入口多、状态源多、维护成本高 |
| 播放队列不可响应 | `PlaylistService` 是普通类，`getPlaylist()` 在 build 中读取，增删队列不会通知 UI | 队列页/当前曲目高亮容易不同步 |
| 播放器职责过多 | `PlayerStateNotifier` 同时更新 AppBar 标题、发通知、记播放统计/历史 | 播放核心被 UI/通知逻辑污染，难测试 |
| 音乐库职责过多 | `LibraryStateNotifier` 同时做扫描、JSON 持久化、播放编排 | 数据层与播放层耦合 |
| 全局状态过重 | `AppBarStateNotifier` 混合主题、语言、用户资料、未读数、动态按钮 | 主题/语言切换依赖「标题栏」这一 UI 概念 |
| Provider 持有 BuildContext | `responsiveContextProvider` 保存 `BuildContext`；`ResponsiveShell` 在 build 中 post-frame 写 provider | 生命周期风险、布局切换用 `AnimatedSwitcher` 重复建树 |
| 视觉装饰过多 | 4 套页面渐变、10 级字体、10 级圆角、彩色阴影、入场动画 | 小窗口里显得吵，信息密度低 |

> 这些问题不是靠继续修 `RenderFlex overflow` 能解决的，需要先收敛信息架构与状态边界。

## 3. 目标信息架构

### 3.1 路由

| 路由 | 右栏内容 | 说明 |
|---|---|---|
| `/` | 重定向到 `/library` | 启动入口 |
| `/library` | 音乐库 | 默认页；搜索、扫描、歌曲列表 |
| `/queue` | 播放队列 | 当前会话队列，可重排/移除/点播 |
| `/settings` | 设置 | 主题、语言、扫描目录、清理数据 |
| `/player`、`/home`、`/search`、`/notifications`、`/scan`、`/history` | 重定向到 `/library` | 兼容旧入口，避免 404 |

- 不再使用 `MenuStateNotifier` 和 `MenuRouteObserver`。当前页由 `GoRouterState.uri.path` 直接决定。
- 左栏播放器不随路由变化，始终存在；路由只切换右栏。
- 设置作为右栏内容而非弹窗，避免小窗口里再叠一层模态层。

### 3.2 尺寸与布局

设计基准不是 600 的窗口外高，而是 **Flutter 可视高度约 560**（Linux GTK 标题栏会占约 37–46px）。

| 项目 | 900×600 默认 | 760×520 最小 |
|---|---|---|
| 全局顶栏 | 44 | 44 |
| 左栏宽度 | 344（约 38%） | 312 |
| 右栏宽度 | 555 | 447 |
| 内容内边距 | 16 | 12 |
| 专辑封面 | 216 | 176–192（按高度自适应） |
| 列表行高 | 52–56 | 48–52 |
| 播放按钮 | 56 | 52 |

实现要点：

- 左栏宽度使用 `LayoutBuilder`：`leftWidth = (maxWidth * 0.38).clamp(312, 360)`。
- 封面尺寸使用可用高度计算：`artSize = min(leftWidth - 48, bodyHeight - 250).clamp(140, 220)`，避免固定值在最小窗口溢出。
- 右栏列表使用 `ListView.builder` + 固定行高，禁止 `Column` 直接铺全部歌曲。
- 中文长标题统一 `maxLines` + `TextOverflow.ellipsis`；时间使用等宽数字。
- 不引入 `AnimatedSwitcher` 切换整页壳层；最多做 120–180ms 的淡入/位移，且只作用于内容区。

### 3.3 页面规格

#### 音乐库

- 顶部：`音乐库 / 播放队列` 页签（高 36），右侧「扫描」「更多」图标。
- 搜索框：高 36，圆角 8，实时过滤（本地过滤，不反复请求扫描器）。
- 工具栏第二行可选显示：歌曲数、当前扫描状态、扫描进度条。
- 歌曲行（高 52）：
  - 左：序号或正在播放图标（20px）。
  - 中：标题（14，单行），歌手（12，单行，次级色）。
  - 右：专辑（可隐藏）、时长（12，等宽）、更多按钮。
- 交互：单击**排进队列并立即播放**（队列里已有的曲目保留，不把整屏列表
  塞进队列；设置里可切成「替换播放队列」，那时队列里只剩这一首）；
  双击**照旧播放并把这首标成喜欢**（设置里可改成双击只加红心、不打断播放）；
  行尾「加入队列」按钮把这一首排进队列；页头「把整个列表加入队列」图标按钮
  一次排入当前可见的全部曲目。
- 空状态：居中图标 + 「还没有音乐」+ 「扫描 ~/Music」按钮 + 当前扫描路径。
- 扫描中：行内进度，不弹全屏加载；扫描完成后自动刷新列表。
- 错误：行内错误条 + 重试，不阻塞整个页面。

#### 播放队列

- 顶部：`播放队列 · N 首`，右侧「清空」。
- 当前曲目高亮（accent 背景 8% + 左侧 2px 竖条）。
- 行高 52：播放图标、标题/歌手、时长、移除按钮。
- 支持拖拽重排；`ReorderableListView` 的 `onReorder` 必须同步更新 controller 状态，不能只改临时 List。
- 双击/单击行播放；空队列显示「从音乐库添加歌曲」。

#### 设置

只保留四组：

1. **外观**：浅色 / 深色 / 跟随系统（三选一分段按钮）。
2. **语言**：下拉选择，沿用现有 `AppLocalizations.supportedLocales`。
3. **音乐库**：扫描目录列表、添加目录、移除目录、立即扫描、清空音乐库。
4. **关于**：版本号、项目地址（可选）。

移除：账户资料、通知开关、开机启动、桌面歌词、字体大小、均衡器、睡眠定时、播放速度预设（速度可后续放入「更多」）。

默认播放器与后台播放（托盘 + 系统媒体控制）不在这里，见 [桌面集成方案](桌面集成方案.md)；设置页为此多一组「桌面集成」。

#### 左栏播放器

- 顶部留 8–12px，不显示返回按钮/更多菜单。
- 封面：圆角 12，无彩色阴影；无封面时用中性色底 + 音符图标。
- 标题：20–22，最多 2 行；歌手 · 专辑：12–13，次级色，1 行。
- 进度条：3px 轨道，滑块 12；时间 11，等宽。
- 控制行：随机/循环 32，上一首 40，播放 56，下一首 40，循环 32（其中随机与循环合并为一个「播放模式」按钮，避免重复）。
- 音量：静音图标 + 80–100px 滑块 + 最大图标；桌面端可 hover 显示。
- 状态：加载中显示轻量 spinner；错误显示一行错误 + 重试。
- 无歌曲：显示「选择一首歌开始播放」，控制按钮禁用，不显示假进度。

### 4.2 状态边界

#### PlaybackState（唯一播放状态源）

```dart
enum PlaybackStatus { idle, loading, playing, paused, error }

class PlaybackState {
  final Song? currentSong;
  final PlaybackStatus status;
  final Duration position;
  final Duration duration;
  final double volume;
  final double speed;
  final PlayMode playMode;
  final List<Song> queue;
  final int currentIndex;
  final String? errorMessage;

  bool get isPlaying => status == PlaybackStatus.playing;
  bool get hasTrack => currentSong != null;
  bool get hasNext => queue.isNotEmpty;
}
```

`PlaybackController extends StateNotifier<PlaybackState>` 负责：

- `playQueue(List<Song> songs, {int startIndex = 0})`
- `playSong(Song song)`（单曲播放时队列只含该曲）
- `togglePlayPause()` / `pause()` / `resume()`
- `next()` / `previous()`（按 `PlayMode` 计算）
- `seekTo(Duration)` / `setVolume(double)` / `setSpeed(double)`
- `cyclePlayMode()`
- `addToQueue(Song)` / `removeFromQueue(int)` / `reorderQueue(int, int)` / `clearQueue()`
- `playAt(int index)`

关键规则：

- **队列在 state 中**，不在 `PlaylistService` 私有字段里。
- **播放完成自动下一首**：通过音频服务的 `completionStream` 触发，不靠 UI 定时器。
- **重复/随机语义**：见 [队列模型方案](队列模型方案.md)。队列即播放顺序；
  随机是队列的一次重排（不是每次现场摇一首），单曲循环重播当前曲，
  上一首优先回到刚播过的那首。
- **副作用出播放器**：播放统计、历史、通知不写在 `PlaybackController` 的核心方法里；需要时由 app 级监听器订阅状态变化。v1 可以只保留统计/历史服务，不接 UI。
- **不再更新 AppBar 标题**，不再读取 `appBarStateNotifierProvider`。

#### LibraryState

```dart
class LibraryState {
  final List<Song> songs;
  final String query;
  final ScanStatus scanStatus;
  final double scanProgress;
  final String? statusMessage;
  final String? errorMessage;

  List<Song> get filteredSongs { ... }

```

`LibraryController` 只负责：加载本地库、扫描、搜索过滤、清空。

- `playSong` 不再放在 LibraryController 里。
- UI 点击歌曲时调用 `listPlaybackProvider` —— 它按设置决定这一首是排进队列
  并立即播放（`enqueueAndPlay`），还是替换整个队列（`playSong`）。
  批量场景走页头的「把整个列表加入队列」按钮：
  `playbackController.addAllToQueue(songs)`。
- 扫描结果持久化从 `LibraryStateNotifier` 移到 `LibraryRepository` / `ScanStorage`，controller 不直接写 JSON 文件。

### 4.4 音频服务调整

在 `AudioPlayerService` 接口中补充事件流，替代 500ms 轮询：

```dart
Stream<Duration> get positionStream;
Stream<Duration?> get durationStream;
Stream<bool> get playingStream;
Stream<void> get completionStream;
```

`JustAudioPlayerService` 直接转发 `just_audio` 的 `positionStream`、`durationStream`、`playerStateStream`、`processingStateStream`。Linux 端 `just_audio_media_kit` 已验证可用，本阶段只加流，不改后端初始化。

这样可以：

- 进度条按真实播放事件更新，CPU 更低。
- 播完自动下一首。
- 暂停/恢复状态由音频后端驱动，减少 UI 与 service 的状态不一致。

### 4.5 设计令牌

新 UI 不再直接使用 500 行的 `AppDesignSystem` 全量令牌，新增一个小型 `CompactTokens`：

```dart
abstract final class CompactTokens {
  static const double space4 = 4;
  static const double space8 = 8;
  static const double space12 = 12;
  static const double space16 = 16;
  static const double space20 = 20;
  static const double space24 = 24;

  static const double radius6 = 6;
  static const double radius8 = 8;
  static const double radius12 = 12;

  static const double icon16 = 16;
  static const double icon20 = 20;
  static const double icon24 = 24;

  static const double rowHeight = 52;
  static const double headerHeight = 44;
}
```

视觉原则：

- **一屏一个视觉焦点**：左栏封面是焦点，右栏列表保持安静。
- **去掉页面渐变**：使用纯色 `surface` / `surfaceContainer`；深色背景 `#121212`，卡片 `#1C1C1E`。
- **保留品牌紫作为强调色**：仅用于播放按钮、进度、当前行、焦点环。
- **边框代替阴影**：列表分隔用 1px `outlineVariant`；只有封面允许轻阴影。
- **动画只保留状态反馈**：hover、按下、播放/暂停图标切换；不做整页入场、旋转封面、频谱条。
- **字体**：沿用平台字体；标题 20/600，正文 14/400，次级 12/400，时间 11 等宽。
